## Multi-agent CLI platform — research findings

```yaml
status: active
updated: 2026-08-01
```

### GitHub Copilot CLI

GitHub Copilot CLI (`gh copilot`) is a GitHub CLI extension providing AI-assisted command-line interactions. Key characteristics:

- **Invocation**: `gh copilot suggest` (command suggestions), `gh copilot explain` (explain shell commands). Operates as a sub-command of the `gh` CLI.
- **Integration model**: Pipes and stdin/stdout. Outputs are shell commands or explanations. Not a persistent subprocess agent — each invocation is a one-shot request.
- **Authentication**: Relies on `gh auth login` (GitHub CLI authentication). Credentials flow through the standard `gh` token store.
- **Programmatic use**: Can be invoked from scripts via `gh copilot suggest --target shell "..."` with `--shell-out` to suppress interactive TUI. Outputs a single command string.
- **Agent applicability**: Best suited for on-demand shell-command generation within processes — e.g., generating a `curl` command for a newly discovered API, suggesting filter syntax. Not a full agent loop provider.
- **Limitations**: No session persistence, no multi-turn conversation, no file editing. Cannot replace codex/claude/gemini for coder or reviewer roles.

### Pi CLI

Pi CLI (Inflection AI's "Pi" personal AI, exposed via CLI wrappers) provides conversational AI access. Key characteristics:

- **Invocation**: Various community CLIs wrapping Pi's API (e.g., `pi-cli`, `piai`). Inflection's official offering is primarily web/mobile; CLI wrappers rely on unofficial API access or the Inflection API for enterprise.
- **Integration model**: Conversational — multi-turn text input/output. Focused on natural-language reasoning and personal assistance rather than code execution.
- **Authentication**: API key-based (Inflection API) or session-token-based (unofficial wrappers).
- **Agent applicability**: Best suited for the `/understand` phase — synthesizing information, making sense of gathered data, formulating decisions. Could assist in `/organize` for schema interpretation. Not suited for code generation or file manipulation.
- **Limitations**: No code execution, no file system access, no tool use. Enterprise Inflection API has rate limits. Community wrappers may break.

### How these CLIs map to the command-phase architecture

| Phase | Primary provider(s) | Copilot CLI role | Pi CLI role |
|---|---|---|---|
| `/explore` | crawl4ai, Playwright, HTTP | Generate scraping commands | — |
| `/seek` | crawl4ai, discovery modes | Generate one-off fetch commands | — |
| `/gather` | discover_jobs.py, providers | — | — |
| `/organize` | deterministic Python | — | Schema interpretation |
| `/understand` | codex/claude/gemini | — | Synthesis, sense-making |
| `/generate` | codex/claude/gemini | — | — |

### Decision record

- **GitHub Copilot CLI** is useful as an auxiliary tool within processes (command generation, script suggestions) but cannot serve as a primary agent provider. It should be integrated as an optional helper available to process steps, not added to `SUPPORTED_PROVIDERS` in `agent_provider.py`.
- **Pi CLI** is useful for natural-language reasoning in the `/understand` phase but lacks tool use. It should be modeled as an optional "reasoning advisor" that can be consulted during sense-making steps, gated behind a capability check.
- Neither CLI replaces the existing codex/claude/gemini provider model. They extend it as specialized tools for specific phases.
- The command-phase architecture (`/explore`, `/seek`, `/gather`, `/organize`, `/understand`, `/generate`) is the unifying abstraction that allows different CLIs to contribute to different stages of the observation pipeline.

## crawl4ai — research findings

```yaml
status: active
updated: 2026-08-01
```

### What crawl4ai is

crawl4ai (`pip install crawl4ai`) is an open-source async web-crawling library built on top of Playwright. It provides:

- **`AsyncWebCrawler`** — async-first crawler that runs a headless Chromium session via Playwright and returns a `CrawlResult` object with raw HTML, cleaned markdown, links, and screenshots.
- **Extraction strategies** — pluggable strategies that transform the crawled page into structured data:
  - `JsonCssExtractionStrategy` — CSS/XPath selectors, fully deterministic, zero API cost.
  - `LLMExtractionStrategy` — uses any LiteLLM-compatible model to extract a structured schema; adds cost and latency.
  - `CosineStrategy` / `BM25ContentFilter` — semantic or keyword-filtered markdown chunks; useful for narrowing long pages.
- **Markdown conversion** — built-in HTML→markdown with `DefaultMarkdownGenerator`, `PruningContentFilter`, `BM25ContentFilter`. Produces clean prose from noisy career pages.
- **Session management** — reuses a named browser context across multiple calls (important for paginated flows).
- **Magic mode** — enables human-like mouse movements and waits; helps bypass Cloudflare-style bot detection.
- **Cookie-consent handling** — configurable `js_code` and `wait_for` hooks that can click accept banners before content loads.
- **Async concurrency** — multiple pages can be crawled concurrently with `arun_many`.

crawl4ai requires Python 3.10+ and Playwright browser binaries (Chromium). Playwright is already a dev dependency at `==1.58.0` (`.arkitype/01-infrastructure.md`).

### Current scraping landscape (from `.arkitype` extraction)

The stack is: **deterministic Python + shell orchestration, no web framework** (`.arkitype/03-software.md`).

| Layer | File(s) | Mechanism |
|---|---|---|
| HTTP + JSON | `discover/http.py` | `urllib` with retry; no JS |
| Static HTML | `discover/sources/generic_html.py`, `static_pages.py` | regex + string parsing on fetched HTML |
| Browser (JS-heavy) | `discover/sources/browser.py` | Playwright sync API; per-source custom logic |
| Detail enrichment | inside `browser.py`, several `_detail` helpers | Playwright navigation + custom text extraction |

Currently registered discovery modes (`.arkitype/03-software.md` → `provider_registry`):

- **JS-heavy browser modes** (candidates for crawl4ai migration): `asml_browser`, `automattic_browser`, `browser`, `coinbase_browser`, `helsing_browser`, `thales_browser`, `trailofbits_browser`
- **Static HTML modes** (potential fallback improvement): `html`, `alphatheta_html`, `harman_html`, `rheinmetall_html`, `thales_html`, `icims_html`, `jobvite_html`, `krisp_html`
- **API/RSS modes** (no crawl4ai benefit): `ashby_api`, `greenhouse_api`, `lever_json`, `workday_api`, `workable_api`, `bamboohr_api`, `eightfold_api`, `teamtailor_api`, etc.

The browser layer is the largest pain point: every JS-heavy source (Meta, Google, ASML, Bosch, Thales, Coinbase, …) requires its own `accept_*_cookies`, `advance_*_results`, `extract_*_jobs` functions. Cookie-consent dismissal alone is duplicated six-plus times.

### `filters` schema constraint (from `.arkitype/02-database.md`)

In `tracks/<track>/sources.json`, the `filters` field is:

```yaml
filters:
  type: object
  required: false
  additional_properties: {type: array, items: string_non_empty}
```

Filter values are **arrays of strings**. CSS selector config for `crawl4ai_browser` must use string arrays (e.g., `"css_container": ["div.job-card"]`), not nested objects. The `discovery_mode` field is enum-validated against `discover.registry.modes` at runtime — adding `crawl4ai_browser` makes it a valid mode.

### Where crawl4ai fits

**Integration point 1 — new `crawl4ai_browser` discovery mode (highest value)**

Add a generic `crawl4ai_browser` provider in `discover/sources/crawl4ai_browser.py` backed by `JsonCssExtractionStrategy`. Sources that need JS but don't need a fully custom strategy can declare `discovery_mode: crawl4ai_browser` with CSS selector config in their `filters` block (all values as string arrays per schema). This is deterministic (no LLM), aligns with the existing registry `SourceAdapter(modes=..., requires=("crawl4ai",))` pattern for graceful degradation, and reduces the amount of source-specific code.

**Integration point 2 — cookie-consent consolidation**

Replace the six-plus per-source `accept_*_cookies` / `dismiss_*_banner` functions in `browser.py` with a shared `js_code` hook or crawl4ai's `wait_for` mechanism. crawl4ai lets you pass `js_code` to execute before extraction; a single "accept-consent" snippet covers the most common patterns (OneTrust, Cookiebot, cookie banners with `[id*=accept]` or `button[aria-label*=accept]` text).

**Integration point 3 — detail-page markdown extraction**

Several `apply_*_detail_text` helpers in `browser.py` and `bundeswehr.py` parse raw fetched HTML into tasks/qualifications sections. crawl4ai's `DefaultMarkdownGenerator` with `PruningContentFilter` could replace these custom parsers when the detail page is structurally predictable but too messy for pure regex.

**Integration point 4 — generic HTML fallback with JS**

`discover/sources/generic_html.py`'s `discover_html` currently falls back gracefully when content requires JS. A `crawl4ai_generic` mode (with LLM extraction opt-in) could serve as the lowest-friction entry point for newly probed sources whose structure is unknown.

### Decision record

- crawl4ai is a good fit for **reducing boilerplate in the browser layer** and **providing a CSS-selector-based generic browser mode**.
- LLM-based extraction (`LLMExtractionStrategy`) is intentionally **deferred**: the existing architecture is deterministic and LLM calls add cost; the option should be made available as an optional flag per-source, not the default.
- The first implementation target is `crawl4ai_browser` + cookie-consent consolidation. See `.manage/plans/2026-08-01-crawl4ai-integration.md` for the step-by-step plan.
- crawl4ai is installable as an optional dependency gated by `requires = ("crawl4ai",)` in its `SourceAdapter`, matching the existing pattern for Playwright-gated providers.

### Risks and open questions

- **Async/sync boundary**: crawl4ai's `AsyncWebCrawler` is async. The registry dispatch is sync (`.arkitype/03-software.md` execution model: "deterministic Python + shell orchestration"). The new provider must wrap `asyncio.run(…)` internally — same pattern as Playwright's own `sync_playwright`.
- **Version pinning**: Only `requirements-dev.txt` exists (no separate production requirements file per `.arkitype/01-infrastructure.md`). Pin crawl4ai there; use `>=0.6,<0.7` or latest stable.
- **`filters` array-of-strings constraint**: CSS selector config must fit the existing schema (`additional_properties: {type: array, items: string_non_empty}`). Nested schemas are not supported; flatten into string lists.
- **Magic mode latency**: Human-like delays increase per-source crawl time; keep opt-in via `"magic_mode": ["true"]` filter flag.
- **LLM secret boundary**: If `LLMExtractionStrategy` is added later, the API key must flow through `scripts/runtime_env.py`, not hardcoded.

```yaml
updated: 2026-08-01
```

### What "Claude skills plugin" means

Claude Code (the Anthropic coding agent) reads agent-instruction files from two locations:

- **Project-local skills**: `.claude/skills/<name>/SKILL.md` — loaded automatically when the agent opens a project directory.
- **Global skills**: `~/.claude/skills/<name>/SKILL.md` — user-wide, loaded in every session.
- **CLAUDE.md / AGENTS.md**: top-level instruction files that compose skills and route modes.

This repo already implements project-local skills: canonical sources live in `.agents/skills/<name>/SKILL.md` and are mirrored to `.claude/skills/<name>/SKILL.md` via `scripts/sync_claude_skills.sh`. The skill files are plain Markdown with a YAML frontmatter block (`name`, `description`).

A **Claude skills plugin** means packaging one or more skill files (and optionally their backing Python machinery) so that another user can install them into their Claude environment without manually copying files from this repo.

### Current skill architecture

| Skill | Purpose |
|---|---|
| `engineering` | Repo-development instructions |
| `explore-start` | Scaffold a new search track |
| `gather-curate-items` | Add/evaluate a single named source |
| `organize-filter-items` | Filter and deduplicate discovery output |
| `understand-prioritize-items` | Score and surface the best matches |
| `explore-discover-sources` | Research and recommend new sources |

All skills are pure Markdown. They depend on the Python scripts in `scripts/` at runtime. Packaging them in isolation (without the scripts) gives an agent the right instructions but no executable backing.

### Packaging options

**Option A — Skills-only distribution (lowest friction)**

Export `.agents/skills/` as a standalone git repository or tarball. A helper script (`scripts/install_skills.sh <target-dir>`) copies the canonical SKILL.md files into `<target-dir>/.claude/skills/`. No Python required; the agent would still need this repo (or a fork) for the scripts.

- Pro: Zero build system; works today with minor scripting.
- Con: Skills without scripts are advisory only — the agent cannot actually run tracks.

**Option B — MCP server (fullest integration)**

Wrap the Python layer as a [Model Context Protocol](https://modelcontextprotocol.io/) server. MCP is Claude's standard protocol for exposing tools to agents. A `tekt-observer-mcp` server would expose tools like `discover_jobs`, `run_track`, `rank_jobs`, and `send_digest`. Users configure it once in `~/.claude.json` (Claude Code) or `claude_desktop_config.json` (Claude Desktop).

- Pro: Claude can invoke the tools directly; skills + scripts become one installable unit.
- Con: Requires an MCP server implementation (Python `mcp` SDK or Node.js `@modelcontextprotocol/sdk`); adds a server process; more surface area.

**Option C — pip-installable package**

Package `scripts/` as a pip package (`tekt-observer`) with console-script entry points (`tekt-discover`, `tekt-run-track`, etc.) and a `tekt install-skills` subcommand that copies the skill files into the caller's project. A `requirements.txt` or `pyproject.toml` would pin the same deps as `requirements-dev.txt`.

- Pro: Standard Python distribution; versioned; `pip install tekt-observer` is familiar.
- Con: Requires `pyproject.toml` authoring; script paths currently assume repo-relative layout.

### Decision record

- **Near-term target: Option B (MCP server)** is the best fit for "Claude skills plugin" semantics, because Claude Code and Claude Desktop both have first-class MCP support and a tool-based interface makes the agent capabilities callable without understanding the script layout.
- **Option A** is a useful interim step: the skill files are already well-structured and can be extracted with minimal work; this unblocks users who want agent instructions even before the MCP server is ready.
- **Option C** may follow naturally from the MCP work once entry points are defined.

### MCP server shape (preliminary)

Tools to expose:

| Tool | Maps to | Description |
|---|---|---|
| `discover_jobs` | `scripts/discover_jobs.py` | Run discovery for one track and date |
| `run_track` | `scripts/run_track.sh` | Full track pipeline (discover + agent + post-process) |
| `rank_jobs` | agent skill invocation | Score jobs against a profile |
| `install_skills` | `scripts/sync_claude_skills.sh` | Copy skill files into a target project |

Entry point: a `server.py` in a new top-level `mcp/` directory, registered in `pyproject.toml` under `[project.scripts]`.

Runtime boundary: the MCP server inherits the same `.env.local` / `JOB_AGENT_SECRETS_FILE` loading as the rest of `scripts/` (via `scripts/runtime_env.py`).

### Constraints and risks

- `scripts/` currently assumes a repo-local `tracks/`, `artifacts/`, and `profile/` layout. Packaging must either bundle path resolution or require the user to set a `TEKT_ROOT` environment variable.
- Playwright browser binaries are heavy (~200 MB). The MCP server should gate browser-based discovery behind a clear capability check, matching the existing `requires=("playwright",)` registry pattern.
- The MCP `python` SDK (`mcp>=1.0`) is not yet in `requirements-dev.txt`. It must be added before implementation begins.
- Versioning: skill files and script logic should be co-versioned in a `VERSION` file so installed skills always match the scripts they depend on.

- Python MCP SDK: https://github.com/modelcontextprotocol/python-sdk

### What browser-use is

browser-use (`pip install browser-use`, Python >= 3.11) is an open-source AI agent framework for browser automation built on Playwright. It lets an LLM-backed agent operate a web browser the way a human does — opening pages, clicking buttons, typing text, filling forms, and extracting structured data. Key capabilities:

- **`Agent`** — the core class. You give it a `task` string and an LLM, and it autonomously plans and executes multi-step browser interactions to complete the task.
- **LLM-agnostic** — works with OpenAI, Anthropic, Google, or browser-use's own optimised `ChatBrowserUse` models via a unified `ChatBrowserUse(model='provider/model')` interface.
- **Async-first** — the agent runs via `asyncio.run(agent.run())`, returning an action history.
- **CLI and skill system** — `browser-use skill install` registers a Claude Code / Codex / Cursor skill that lets an outer agent invoke browser-use as a sub-tool; `browser-use` CLI provides direct task execution.
- **MCP support** — browser-use exposes its agent as MCP tools, enabling integration into agent orchestrators.
- **Custom tools** — the agent can be extended with user-defined Python functions.
- **Session management** — persistent browser contexts for multi-step workflows.
- **Stealth and anti-detection** — human-like interactions; optional cloud browsers with proxy rotation and captcha solving.

browser-use requires Playwright browser binaries (Chromium). Playwright is already a dev dependency at `==1.58.0`.

### How browser-use differs from crawl4ai

| Aspect | browser-use | crawl4ai |
|---|---|---|
| Primary purpose | AI agent that *operates* a browser (click, type, navigate) | Library that *crawls and extracts* structured content from pages |
| Automation model | LLM plans each action; non-deterministic | Deterministic CSS/XPath extraction; optional LLM extraction |
| Cost profile | LLM call per action step; higher cost per page | Zero LLM cost for `JsonCssExtractionStrategy`; LLM optional |
| Best for | Interactive flows (login, pagination, form filling, unknown page structures) | Bulk extraction from pages with known structure |
| Output | Action history, extracted data as agent response | `CrawlResult` with HTML, markdown, structured JSON |
| Session reuse | Persistent browser contexts | Named session contexts |

**They are complementary, not competing**: browser-use excels at *discovering how to navigate* a site (what buttons to click, how pagination works, where job listings appear), while crawl4ai excels at *extracting data at scale* once the structure is known.

### Where browser-use fits in the tekt.observer stack

**Integration point 1 — Source-structure discovery driver (highest value)**

Use browser-use as a *reconnaissance* tool during source setup (`explore-start` skill). When adding a new employer's career page:
1. Point a browser-use agent at the careers URL with a task like "Find all job listings on this page, describe the page structure, identify CSS selectors for job cards, titles, locations, links, and describe how pagination works."
2. The agent navigates the page (handling cookie consent, scrolling, clicking "Load more"), and returns a structural description.
3. This output feeds directly into `sources.json` config: the CSS selectors become `filters` values for the `crawl4ai_browser` discovery mode.

This eliminates the manual "inspect element → write custom extraction code" step for each new source.

**Integration point 2 — Interactive scraping for complex sources**

Some career pages require multi-step interaction that CSS selectors alone cannot capture (e.g., search-form submission, accordion expansion, infinite scroll with authentication). browser-use can handle these as a `browser_use` discovery mode:
- The agent receives a task template with employer-specific parameters from `sources.json`.
- It navigates, interacts, and returns structured job data.
- This is higher-cost (LLM per action) but eliminates the need for per-source custom Playwright code in `discover/sources/browser.py`.

**Integration point 3 — tekt.observer as browser-use skills**

Package tekt.observer workflows as browser-use custom tools or as a skill set that a browser-use agent can invoke:

| Skill / Tool | Purpose |
|---|---|
| `discover_jobs` | Run discovery for a track; return new listings |
| `evaluate_source` | Check if a careers URL is scrapable; recommend discovery mode |
| `rank_jobs` | Score discovered jobs against a profile |
| `probe_source` | Navigate a career page and extract its structure for config |

This makes tekt.observer's data-gathering capabilities available to any agent using browser-use as its browser backbone.

**Integration point 4 — Complete data-gathering plugin architecture**

The combination of browser-use + crawl4ai + tekt.observer scripts forms a three-layer plugin:

```
┌─────────────────────────────────────────────────┐
│  Agent layer (browser-use)                      │
│  - Navigates unknown pages                      │
│  - Discovers page structure                     │
│  - Handles interactive flows                    │
├─────────────────────────────────────────────────┤
│  Extraction layer (crawl4ai)                    │
│  - CSS-selector-based bulk extraction           │
│  - Markdown conversion                          │
│  - Cookie-consent consolidation                 │
├─────────────────────────────────────────────────┤
│  Orchestration layer (tekt.observer scripts)    │
│  - Track management                             │
│  - Source registry and scheduling               │
│  - Deduplication, ranking, digests              │
└─────────────────────────────────────────────────┘
```

### Decision record

- browser-use is a good fit as a **discovery/reconnaissance driver** that feeds CSS selectors and navigation instructions into crawl4ai's deterministic extraction.
- browser-use as a **runtime discovery mode** (`browser_use`) is feasible but higher-cost; it should be opt-in for sources that genuinely require interactive navigation.
- Packaging tekt.observer capabilities as browser-use custom tools creates a **complete open-source signals plugin** — browser-use navigates, crawl4ai extracts, tekt.observer orchestrates.
- browser-use's `skill install` command is designed for Claude Code / Codex integration. This aligns with the existing MCP server plan (RM-017) — browser-use skills could coexist with or complement the tekt-observer MCP server.
- The browser-use agent requires an LLM API key at runtime, which must flow through `scripts/runtime_env.py` (same boundary as the deferred crawl4ai LLM extraction strategy).

### Risks and open questions

- **LLM cost**: Every browser-use agent run incurs LLM API costs. Discovery mode tasks (finding page structure) are infrequent and bounded; runtime scraping tasks are frequent and could be expensive. Mitigate by using browser-use only for discovery/setup, not routine extraction.
- **Non-determinism**: browser-use's LLM-driven navigation is inherently non-deterministic. Outputs should be validated and captured as deterministic config (CSS selectors in `sources.json`) before being used in production runs.
- **Version compatibility**: browser-use requires Python >= 3.11. The repo currently uses `requirements-dev.txt` for deps; browser-use should be added as an optional dependency.
- **Async boundary**: Same as crawl4ai — browser-use is async-first; the registry dispatch is sync. Wrap with `asyncio.run()`.
- **Skill install scope**: `browser-use skill install` registers a skill in the local Claude Code environment. This is a user-local action, not a repo-level change — document it in machine setup, not in repo config.
