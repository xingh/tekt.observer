## /explore — Crawl and discover

```yaml
status: active
updated: 2026-08-01
```

**Purpose**: Probe an unknown or partially known URL to identify what data is observable and how it's structured.

**Trigger**: User provides a URL or domain to investigate.

**Steps**:

1. Validate the URL is reachable (HTTP HEAD check).
2. Attempt static fetch first (`discover/http.py` pattern). If content requires JS, escalate to browser.
3. Launch crawl4ai `AsyncWebCrawler` with the URL. Capture:
   - Page title and metadata
   - Main content structure (headings, lists, tables, cards)
   - Links to subpages (pagination, detail pages)
   - Any structured data (JSON-LD, microdata)
4. If `gh copilot` is available and `TEKT_AUX_PROVIDERS` includes `copilot`, optionally suggest scraping commands for discovered API endpoints.
5. Output an exploration report: `artifacts/exploration/<domain>/<date>.json` containing page structure map, recommended selectors, pagination pattern, and confidence score.

**Outputs**: Exploration artifact (JSON), recommended sensor config (draft), list of follow-up URLs.

**Idempotency**: Re-running `/explore` on the same URL updates the artifact with fresh observations. Previous artifacts are preserved with date suffixes.

## /seek — Directed retrieval

```yaml
status: active
updated: 2026-08-01
```

**Purpose**: Once a source has a working sensor (generated or manually authored), fetch specific information on demand.

**Trigger**: User or automation requests data from a connected source with parameters (e.g., search terms, filters, specific page).

**Steps**:

1. Load the source's sensor definition (from `sources.json` or sensor config).
2. Validate the sensor is functional (last health check timestamp, canary test if stale).
3. Execute the sensor with provided parameters — dispatch through the appropriate discovery mode.
4. Return raw results without aggregation or schema mapping.
5. Update `source_state.json` with seek timestamp.

**Outputs**: Raw fetch results (JSON), updated source state.

**Idempotency**: Each seek is additive. Same parameters produce same results (subject to source-side changes). No side effects beyond state timestamp.

## /gather — Aggregate from source

```yaml
status: active
updated: 2026-08-01
```

**Purpose**: Pull bulk data from one or more connected sources. This is the generalized form of today's discovery runs.

**Trigger**: Scheduled cadence, manual invocation, or phase-chain from `/seek`.

**Steps**:

1. Determine which sources are due (cadence logic from `source_state.json`).
2. For each due source, run its sensor with configured search terms and filters.
3. Collect all results into a dated aggregate artifact.
4. Track per-source status (complete, partial, failed) in source state.
5. Emit progress events for long-running gathers.

**Outputs**: Aggregate artifact (`artifacts/discovery/<track>/<date>.json`), updated source state.

**Idempotency**: Re-running gather for the same date overwrites the artifact. Source state advances only on complete status.

**Current implementation**: `scripts/discover_jobs.py` — this process describes its generalization.

## /organize — Schema mapping

```yaml
status: active
updated: 2026-08-01
```

**Purpose**: Transform raw gathered data into a specific schema for downstream consumption.

**Trigger**: Automatically follows `/gather`, or manually invoked on existing artifacts.

**Steps**:

1. Load the target schema definition (currently implicit in digest JSON schema; will be explicit per data type).
2. For each raw record in the gather artifact, apply field mapping and normalization:
   - Deduplicate by key (normalized company + title + URL for jobs)
   - Normalize dates, locations, URLs
   - Extract and tag structured fields (requirements, skills, seniority)
3. Validate organized records against the schema.
4. Output the organized dataset.

**Outputs**: Schema-conforming structured data (JSON), validation report.

**Idempotency**: Pure transform — same input always produces same output. No external side effects.

**Current implementation**: Partially in `organize-filter-items` skill (filtering/dedup) and `digest_json.py` (schema output).

## /understand — Sense-making and decisions

```yaml
status: active
updated: 2026-08-01
```

**Purpose**: Interpret organized data, identify signals, and make decisions (rank, filter, categorize, alert).

**Trigger**: Follows `/organize`, or invoked on existing organized data.

**Steps**:

1. Load organized data and user context (profile, preferences, history).
2. Invoke the primary agent provider (codex/claude/gemini) with the analysis prompt and data.
3. Optionally invoke Pi CLI (if available and enabled) for supplementary reasoning on ambiguous items.
4. Agent produces:
   - Rankings/scores per item
   - Category assignments
   - Signal detection (new patterns, anomalies, opportunities)
   - Decision recommendations (apply now, watch, skip)
5. Output structured understanding results.

**Outputs**: Ranked/annotated dataset (JSON), decision log, signal alerts.

**Idempotency**: Agent output may vary between runs (LLM non-determinism). Results are always additive — new understanding enriches rather than replaces previous assessments. `times_seen` and `highest_score` accumulate.

**Current implementation**: `understand-prioritize-items` skill + `update_ranked_overview.py`.

## /generate — Output production

```yaml
status: active
updated: 2026-08-01
```

**Purpose**: Produce human-readable or machine-readable output from understood data.

**Trigger**: Final phase in pipeline, or on-demand for specific output formats.

**Steps**:

1. Load understanding results and select output format(s):
   - Markdown digest (`render_digest.py`)
   - Email body (`send_digest_email.py`)
   - Telegram message (`send_digest_telegram.py`)
   - Logseq page (`sync_to_logseq.sh`)
   - JSON export (structured digest)
   - Custom format (future: web UI, RSS feed, webhook)
2. Render output using the appropriate template/renderer.
3. Deliver to configured targets.
4. Update delivery state (last sent timestamp, delivery status).

**Outputs**: Rendered artifacts (markdown, HTML, JSON), delivery confirmation.

**Idempotency**: Rendering is pure (same input → same output). Delivery is idempotent per date-target pair — re-sending the same digest to the same channel is safe (message is replaced or deduplicated).
